# Review: paper vs implementation (2026-10-09)

> **Status note (2026-10-10).** This is a dated review. Status notes added on
> 2026-10-10 are marked *2026-10-10*; everything else is as written on 2026-10-09.

Scope: `paper/paper.md`, `crypto/` (cu-crypto, zkbench circuits, cu-sidecar, reference client),
`routstr-core` branch `confidential-upstream`, `routstrd` / `routstr-sdk` branches. Includes a live
end-to-end run against real `api.venice.ai` through a temporary local node (Nostr publishing
blackholed) with a local fake-wallet Cashu mint.

**Bottom line.** The cryptographic core is sound: the key schedule, GCM, nonce handling and the
circuits check out, and every value the proofs compute is asserted. The *wiring around* the proofs
did not do what the paper claims. Before this review, the node could read every prompt and response
(the client disclosed `HS`), and a client could bypass parameter pinning and billing. Those are now
fixed and re-tested live. When §1 was written (about 13:45), the routstrd/SDK integration the paper and
README describe did not exist yet; §6 records it landing later that day, and §7–§8 describe it.
*2026-10-10:* the integration is complete on all three branches and was re-verified end to end.

## 2. Critique of the paper

*2026-10-10:* these are the point-in-time critiques of 2026-10-09. Each item now carries a status
line; the paper was revised accordingly.

1. **P1 rests on an unstated assumption.** §5 says the client "cannot read the key (the keystream
   is independent of the plaintext)". In fact the client holds the *whole* epoch-1 key `K_1`, since it
   must seal KU1 at seq 1. The API key is therefore exactly `C_1 ⊕ S`, and it is protected only by C
   never seeing `C_1`. Any observer on the N→U path that colludes with C learns the key: a shared
   cloud network, a CDN or TLS-terminating middlebox log, or a compromised router. So does any
   upstream behaviour that reflects request bytes (error pages echoing paths or headers). The
   material-swap bug (#4) turned this into a practical attack. The paper should state the
   assumption, and recommend scoped, low-limit, rotating upstream keys. A stronger design derives
   `c_ap_1` in 2PC so that neither party holds `K_1`; that MPC covers only one record and is cheap
   compared to MPC-TLS.
   *Status 2026-10-10:* stated in the paper (§5, P1), with the 2PC upgrade framed as a new protocol
   version with its own key ownership and proof binding.
2. **π_N's "detectable after the fact" is circular.** The node signs its own attestation, so it can
   commit honestly and write a different head of the same length: a different account, endpoint,
   or a header that enables provider-side retention or logging. C cannot observe that. Residual
   risk 1 is real, and should not be described as "disputable".
   *Status 2026-10-10:* the paper states it as residual risk 1, and §4.3 no longer claims detection.
3. **Third-party verifiability is overstated (abstract, P4, table in §8).** The proofs are
   interactive and designated-verifier. The receipt is only N's signature. C holds `s_ap_0`, so C can
   forge server records itself. Neither party can convince a third party of what U actually
   reported. "Verifiable by any third party holding the receipt" should be removed or qualified.
   *Status 2026-10-10:* an explicit non-goal; the paper also notes that a non-interactive backend
   alone would not change this.
4. **Escrow sizing is not sound for multimodal or tool inputs.** Bounding input tokens by body bytes
   fails when a short `image_url` or file reference expands to thousands of tokens, or when
   provider tools such as search add tokens. Either pin or forbid those fields in the private part,
   or price them separately.
   *Status 2026-10-10:* resolved. The reservation covers the model's full context window, search and system-prompt injection are pinned off, and the offer lists only models that
   reject image parts (`crypto/tools/regression-modality.py`).
5. **The abort rule rewards a malicious node.** "Abort after head, no usage event → N keeps E" means
   N can cut the stream before the usage event and keep the maximum escrow. C cannot prove who
   aborted. The paper compares this with prepaid flows, but there the node does not gain from
   failing. Consider refunding a fixed share of E, or N having to show the upstream closed early.
   *Status 2026-10-10:* unchanged by design and stated as residual risk 8 (balances rest on N's
   goodwill after an abort, as in the existing Routstr design).
6. **Traffic analysis is understated.** N sees one TLS record per streamed token, so it sees the
   token-length sequence of the response. This side channel is known to reconstruct a large share of
   LLM responses (Weiss et al., USENIX Sec 2024). It is more than "volume and timing" and should be
   discussed. The client cannot pad server records.
   *Status 2026-10-10:* discussed in the paper as residual risk 2.
7. **The latency headline is a best case.** The +0.49 s / +0.90 s numbers come from client, node and
   sidecar on one machine. The paper's own WAN column shows π_C1 alone at 1.53 s with 25 ms one-way
   delay, and the handshake via the relay adds C↔N round trips. The comparison table's "~0.5 s"
   should show a WAN figure next to it.
   *Status 2026-10-10:* the paper gives the WAN proof costs and labels the end-to-end figures as
   single-host best cases.
8. **Parameter pinning depends on parser differentials.** Last-wins was tested black-box at one
   point in time. Gateways and backends often use different JSON parsers. The regression suite
   mentioned in A.2 does not exist in the repo.
   *Status 2026-10-10:* resolved. `crypto/tools/provider-profile-check.py` (A1–A11, 11/11 live, with
   negative controls) and `crypto/tools/regression-modality.py` are the regression gates; the paper
   words profile items (5)–(6) as requirements supported by sampled tests.
9. **The paper and the code disagree** on `HS` disclosure (#1), the agreed suffix (#2/#3) and tail
   anchoring (#8). Section 6.3 ("all four proofs verified") was true but meaningless while #1 held.
   *Status 2026-10-10:* resolved by the fixes in §1.

## 3. Measurements (live, real Venice, `gemini-3-flash-preview`, max_tokens 12, M-series Mac)

Client, node and sidecar run on one host, so there is no C↔N WAN. All runs use the fixed code.

**Interleaved run** (8 rounds of direct → node proxy → confidential, so upstream drift hits all
three equally). All 8 confidential sessions succeeded:

| path | TTFT median | total median | added TTFT / total vs direct |
|---|---|---|---|
| direct HTTPS to Venice | 1380 ms | 1477 ms | – |
| routstr node proxy (API key) | 1206 ms | 1221 ms | −174 / −256 ms (the node reuses a warm upstream connection) |
| **confidential (cold, all 4 proofs)** | **2016 ms** | **2513 ms** | **+637 / +1036 ms** |

**Batch run** (10 runs each, one retry needed per mode): direct 1409 / 1472 ms; confidential cold
1822 / 2314 ms (**+414 / +843 ms**); π_C1 486 ms; handshake through the relay 89 ms.
**Pre-warmed (armed)**: claim → first token 1047 ms, with claim → body 2 ms. The proof overhead
disappears from the request path. The cost is a 639 ms arm step done ahead of time, plus an
upstream connection held open per armed session.

Venice's own TTFT varied between about 1.0 and 1.5 s over the hour, which is the same order as the
protocol overhead. Paper's claim (+0.49 s / +0.90 s) is **reproduced within noise** (+0.41…0.64 s
TTFT, +0.84…1.04 s total), as a localhost best case.

**routstrd** (from source, scratch config, fake-mint wallet → node → Venice, normal non-confidential
path): works, with a TTFB median of about 1.2 s. The node had to be injected by hand. routstrd only uses
providers discovered on Nostr, its HTTP fallback directory `api.routstr.com/v1/providers/` returns
404, and loopback nodes come "DISABLED (nostr review)". A private or unannounced node cannot be used
even with `--provider`.

## 4. Other findings from the e2e run

- **The earlier prototype node was publicly announced.** routstrd's Nostr discovery lists
  `http://127.0.0.1:8000/`, which is the node started per `crypto/PROGRESS-CONFIDENTIAL.md`
  (`HTTP_URL=http://127.0.0.1:8000`, default relays). The announcer only skipped the exact string
  `http://localhost:8000`. Fixed in `routstr/nostr/listing.py`: loopback, private and link-local
  hosts are never announced. The existing public event should be deleted (NIP-09) with that test
  identity. This test run used blackholed relays (`Published … to 0/1 relays`).
- The node's generic `UPSTREAM_BASE_URL` provider forwards OpenRouter-style ids
  (`google/gemini-3-flash-preview`) to Venice, which answers 404. Normal proxying needed the provider
  type switched to `venice`. The confidential path is unaffected, because the client writes the
  model itself.
- The node seeds `openai` and `anthropic` provider rows from ambient env keys on a fresh DB. Be
  careful running test nodes from a shell that has real keys.
- The adversarial checks were re-run live against the fixed sidecar: a client sending `HS`, a wrong
  suffix, and skipping π_C2 are all rejected. In the ledger the first is `refunded` (head never
  written) and the other two are `kept`. No API key, `HS` or `c_ap_1` appears in any log or
  run artifact.

Found while doing this: settlement priced a model at the *best-ranked*
provider's rates, not those of the provider behind the sidecar. It now uses the
